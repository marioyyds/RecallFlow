# 2026-10-22

## 排查 verifier 的两个线上症状（未改代码，仅诊断）

用户反馈：① 长上下文/复杂任务时"最后校验阶段卡死"；② 经常反复校验。

### 定位到的主因（已用探针实证）

**P0：校验超时被误判成用户中断，且该分支不发 end 事件 → 前端永久 waiting**

链路：
- `llm.js:16` 内部 `setTimeout(() => controller.abort(), 15000)`（verifier 传 15000）
- abort → fetch reject `DOMException`，`name === 'AbortError'`
- `llm.js:86` `isRetryableError` 把 AbortError 判为不重试（无法区分"用户中断"与"内部超时"）
- `verifier.js:84` `if (e.name === 'AbortError' || signal.aborted) throw e` → 抛
- `agent.js:607` `classifyVerifyOutcome` → `{kind:'interrupt'}`
- `agent.js:2072-2077` 只 `persist(...)` + `return`，**没有 emit({type:'end'})、也没有 emitState**
- run-hub 只有 `case 'end'` 才把 status 置 ended → 面板永远停在 running = 用户看到的"卡死"

探针输出（mock fetch，signal 从未 abort）：超时错误 name=AbortError、timeout标记=false、会重试=false；verifyCompletion 直接抛出 AbortError。

**次要：** 校验调用未传 `max_tokens`、未开 `response_format: json_object`；15s 硬超时对长 evidence 偏紧；超时若以 TypeError 形式冒出则会被重试 3 次（≈46s 卡顿）。

**反复校验的成因（未实证，代码推理）**
- `verificationCount` 只在否决时 +1（agent.js:2035 / 2086），上限 `maxVerifications: 2`
- **无证据指纹去重**：证据与 claim 未变时仍会再调一次 LLM，同输入同 prompt(temperature 0.3) → 大概率同样否决
- **precheck 与 LLM 校验共用同一个配额**（2016 与 2055 都判 count<2），确定性规则命中会吃掉 LLM 校验的机会
- 否决后反思只要求"换做法"，不强制产生新证据 → agent 容易直接再调一次 complete_task
- **`final-answer` 收尾路径（2147-2155）完全不校验** → 被否决后可改口直接回答绕过护栏

### 已实施（P0 + 治反复校验）

- `llm.js`：内部超时翻译成 `TimeoutError` + `timeout=true`（`catch` 里判 `timedOut && !signal.aborted`）；`isRetryableError` 对 timeout 返回 false；body 支持 `maxTokens` / `jsonMode`。
- `verifier.js`：中断判据改为**只看 `signal.aborted`**（不再看 `e.name`），其余一律 fail-open；超时 15s → `VERIFIER_TIMEOUT_MS = 25000`；校验调用传 `maxTokens: 400` + `jsonMode`；新增 `buildRepeatedVerificationReflection`。
- `agent.js`：interrupt 分支补 `emitState(CANCELLED)` + `emit end` + 关辅助页（原先唯一一个只 persist 不发事件的出口）；确定性预检改用 `deterministicFails` 独立配额（不再挤占 LLM 校验次数）；新增 `verifyEvidenceSignature` + `lastDeniedSignature`（持久化）—— 同一证据重复送审直接短路，不调模型。
- `run-hub.js` / `chat.js`：`inconclusive` / `repeated` 两种 verify 事件分开渲染，修掉"校验未通过：…已按通过放行"的自相矛盾文案。
- 已重建 `content.js`（34 模块 / 423 KB）。
- 测试：新增 `tests/verifier-timeout.test.mjs`（8 条，行为断言）；4 条接线门禁并入 `completion-verification.test.mjs`（复用其 src，避免触发棘轮）。`npm test` 全绿：1854 项 / 160 文件。

### 第二轮（同日，继续）

- `agent.js` final-answer 收尾路径补上**确定性预检**：`claim = step.assistantMessage.content`，命中规则就 `deterministicFails += 1` + emit(`source:'final-answer'`) + push 反思 + `continue`。只跑零成本规则、不追加 LLM 校验（长叙述没有可对齐的 claim，误判率高且多花 25s）；配额复用 `deterministicFails`（≤2），避免"改口→再被否"循环。这是本次唯一真正的护栏缺口：被否决后改成直接输出最终回答即可绕过。
- `evidence.js` **实测后决定不改**：`selectEvidence` 在 10 万字全文 + 14 tokens 上平均 **0.4ms**（V8 的 indexOf 是 SIMD，293 次全文扫描才 0.4ms）。上一轮"长页面同步阻塞"的判断被自己的测量推翻 —— 不要为假想的性能问题增加复杂度。
- 遗留（很小）：`MAX_TOKENS = 30` 的注释说"最多用 30 个关键词检索"，但 `selectEvidence` 未对过滤结果切片，实际最多检索 120 个（`extractClaimTokens` 返回 `MAX_TOKENS*4`）。实测代价可忽略，改切片反而会丢掉长中文片段（它们在 token 顺序里排最后），故维持现状。
- 门禁新增 1 条（并入 `completion-verification.test.mjs`，仍复用其 src，棘轮未破）。`npm test` 全绿：**1855 项 / 160 文件**；`content.js` 已重建（24 模块 / 423 KB）。

### 第三轮：真模型验证 + 一个把改动吞掉的工具链缺陷

**真模型 eval（deepseek-flash，用户临时提供的 key，未写入任何文件）**
跑了 3 个针对性剧本，全部通过、无卡死：
- `site-search` 12.7s / 7 请求 / 校验器 1 次
- `recover-from-rejection` 28.0s / 13 请求 / 校验器计数 3（trace 证实**只有 1 次真实校验否决 + 1 次确定性规则命中**，第 3 条是 429 重试产生的请求，非重复校验）
- `annotate-highlight` 10.4s / 6 请求 / 校验器 1 次
- 附带发现：`printTrace` 的"请求数"口径会把 HTTP 重试算进去，不能直接当校验次数用；准确口径是 run trace 里的 `phase:'verify'` 事件（存 `chrome.storage.session` 的 `recallflow.runTrace.v1.<runId>`）。

**第三个延迟来源（已修）**：`callDeepSeek` 对 429/5xx 默认重试 2 次，校验单次预算 25s 会被叠成最坏 ≈76s。校验器改为 `maxRetries: 0`（fail-open 的安全网，重试换不来护栏强度）。`llm.js` 新增 `settings.maxRetries`，默认仍是 2。

**⚠ 重大工具链缺陷（已修）**：`scripts/lib/mutation-fs.mjs` 的崩溃自愈判据原为 `current.includes(meta.to)`，而 `to` 常常是 `  return false;` 这类满文件都有的片段 ⇒ 判据恒真 ⇒ **任何一次运行留下的旧备份，都会在下一次启动时覆盖比它更新的源码**。后果：`agent.js` 里刚加的 final-answer 校验段被静默回退，而 `npm test` 全程"通过"（收尾核对 `after === raw` 看到的正是旧备份的内容）。
- 修法：`writeBackup` 记录 `from`；`recoverLeftovers` 改为**精确重建比对**（`norm(current) === norm(backup).replace(from,to)` 才还原），否则只删备份、绝不覆盖。
- 新增 2 条门禁（`tests/mutation-guard.test.mjs`）：to 为通用片段时旧备份不得覆盖新代码；停在变异态仍能还原（收紧判据不能废掉自愈）。
- 遗留：`removeBackup` 在**脚本进程内**删除失败（文件本身手动可删，14/14 OK，疑为 Windows 杀软/索引服务占句柄），每轮仍留 `.mutation-backup*`。已加收尾兜底 + `（已清理残留备份）` 日志，但进程内删除仍未生效，**未定位**。危害已被判据修复消除，残留文件已在 `.gitignore` 中。

**教训**：`npm test` 里的变异测试会就地改写源码；它留下的任何残留都是"能覆盖新代码"的弹药。改动源码后如果 `npm test` 报"找不到锚点"，先确认不是被旧备份回退了。
