## 1. 先说一个被手算掩盖的事实

`docs/tool-design.md` §10 原先写这条路径"目标落在 ~28"。**把每一档的净减量加起来，实际是 55 → 33**，
只省下 22 个。要落到 28 还差 5 个，要落到 §10 自己写的 ≤25 还差 8 个。

那 5～8 个的差距**不可能靠"合并同类"补上** —— 剩下的多数是语义各自独立的工具。
因此接下来必须明确：**是接受 33，还是砍能力**。这个判断我无法替你下，但它现在是可量化的。

## 3. 三个必须遵守的约束（否则"合并"会变成"降级"）

1. **权限取最高**：一组里只要有一个 `destructive` / `alwaysRequireApproval`，合并后的工具必须继承它。
   §2 已逐档列出依据。**这一条有真实的失败先例**：`run_macro` 曾因执行期没有白名单而绕过
   `alwaysRequireApproval`，等同于提权。
2. **`readOnly` 不可放宽**：一组里混有读与写时，合并后的工具不能再被当作只读，
   否则"只读工具"这条捷径会变成写操作的绕过路径。
3. **`alwaysAvailable` 谨慎继承**：它会进入每一轮请求的签名（token 成本 × 轮数）。
   合并后若把一组都标为 `alwaysAvailable`，等于把省下的 token 又加回去。

## 6. 建议的最小可执行路径

若你希望先拿到收益而不承担风险：**只做第 1–3 档**（视觉标注 / 元素检查 / 诊断）。

- 收益：当前 53 → 46（原按 55 起算时写的是「55 → 46，省 9 个」；诊断档已先执行，故现在剩 7 个可省）；
- 风险最低：三档内部**权限完全一致**（分别是 `page+审批`、`read`、`read`），不存在"取最高"的歧义；
- 不触碰最高频的 `click_element`，也不砍任何能力面；
- 每档可独立验证（跑现有 906 项单测 + 7 个 E2E 场景）。

**但请注意**：第 3 档已执行，剩下的第 1、2 档**引用密度都很高**（视觉标注 ~95 处、元素检查 85 处），
每档都需要**单独一轮完整预算**（含 `lib/shared/utils.js` 的文案、`constants.js` 的常量、
`skill-defs.js` 的技能清单、以及 8 个测试文件的同步）。
若预算有限，**优先挑引用密度低的档**（第 5 档宏）—— 引用密度才是决定一轮能否做完的指标，
而不是"权限是否一致"。（原先这里还推荐了第 7 档帧+AX，**实测后已撤回**，原因见 §8。）

做完这三档后，若效果符合预期，再按 §2 的顺序往下推。

## 8. 各档的"跨越性约束"核对结果（2026-02 实测）

表格里的"可重构"是**语义判断**；但合并能否成立还取决于**实现约束**。逐档核对后：

| 档 | 跨越性约束 | 结论 |
| --- | --- | --- |
| 1 视觉标注 | 无（四者都走 `executePageTool`，同一路径） | 可做，但**引用密度高**（~95 处 / 8 个测试文件） |
| 2 元素检查 | 无（五个都是 `read`，同一路径） | 可做，引用密度高（85 处） |
| 3 诊断 | 无 | ✅ **已执行** |
| 4 知识库条目 | 无（含 `destructive`，权限取最高即可） | 可做 |
| 5 宏 | 无，但**必须按 op 分别保留审批与回放白名单**（见下） | 可做 |
| 6 技能 | **有**：族里现在含 `save_skill`（`high` + `alwaysRequireApproval`），按 op 分级审批做不到 | ⚠ **不建议**（省 2 个，代价是高频的 `load_skill` 变成逐次审批，或两个写闸门一起丢） |
| 7 帧 + AX | **有**：`get_ax_snapshot` 需要 CDP，`list_frames` 刻意不依赖 CDP | ⚠ **不建议**（省 1 个不划算） |
| 8 指针族 | 无，但会削弱最高频工具的签名 | 需取舍 |
| 9 用户脚本 | 需砍能力面 | 需取舍 |

**第 5 档（宏）的硬约束**：`run_macro` 曾因**执行期没有白名单**而能回放 `run_javascript`，
绕过 `alwaysRequireApproval` —— 等同于提权。合并成 `macro(op)` 时，
"保存要审批 + 回放要过 `REPLAYABLE_TOOLS` 白名单"这两条防线**必须按 op 分别保留**，
不能因为"合并成一个入口"就统一放行。`tests/tool-merge-plan.test.mjs` 已把它写成断言。

**教训**："语义上属于同一类"不等于"可以合并"。第 7 档就是反例 ——
它看起来最干净（都是"结构视图"、都是 `read`），却因为一个**能力前置条件不同**而不能合并。
判断合并可行性至少要问三件事：

1. **引用密度** —— 决定工作量（第 1 档 95 处 ≠ 第 3 档低密度）；
2. **权限取谁** —— 决定安全性（知识库含 `destructive`、技能升 `external`）；
3. **能力前置条件是否一致** —— 决定能否成立（第 7 档的 CDP 差异）。
