# 真实页面测试 + 持续改进方案

> 目标：在**真实页面**上验证「操作页面所有元素」这类能力（点击、搜索、多步操作、加阴影、
> 划重点、站点 AI 助手、检索调研、发小红书），并把实测结果**回灌**到 skill / 工具定义 /
> agent 编排里。本文是可执行方案，不是现状描述。

## 一、现状：已经有很强的三层，缺的是「真实页面」这一层

仓库已有一套成熟机制（见 [e2e-testing-guide.md](e2e-testing-guide.md)）：

| 层 | 做什么 | 进 CI | 位置 |
| --- | --- | --- | --- |
| ① 能力验收 | 夹具页 + 脚本化模型，断言**页面真的到了目标状态** | 是 | `tests/e2e/`、`tests/e2e/fixtures/` |
| ② 技能契约 | 技能声明的工具 ⊇ 剧本实际用到的工具（静态） | 是 | `tests/skill-playbook-contract.test.mjs` |
| ③ 技能有效性 | 真模型跑同一批剧本，看完成率与工具轨迹 | 否（花钱、非确定） | `tests/e2e-eval/`、`scripts/eval-real-model.mjs` |

三层已经能回答「这套能力成立吗」和「文案对真模型有没有用」。它回答不了的是：

- 定位器在**真实 DOM** 上的成色（SPA 时序、shadow DOM、广告位、反爬弹窗、登录态）；
- 「检索调研 / 站点助手 / 发小红书」这类**跨页面、长流程**能力的真实成色；
- 日常使用的**编排开销**（轮次、缓存命中、重试、绕路）。

所以方案是：**四层测试阶梯** + 一个**失败归因 → 改进**的固定闭环。

## 二、四层测试阶梯

### T0 · 夹具 E2E（确定性，进 CI）—— 补能力剧本

按既有五件套补剧本：夹具页 + 剧本（`tools` 作契约锚点）+ 真浏览器 E2E + 内置技能 + 契约门禁。
本批新增四个（已完成）：

| 剧本 | 触发词 | 夹具页 | 真正要造出的难点 |
| --- | --- | --- | --- |
| `annotate-highlight` | 划重点 | `/hl` | 高亮是视觉浮层，达标可以靠"删/藏内容"作弊 |
| `control-shadow` | 加阴影 | `/ui` | 「已修改 N 个元素」≠ 样式真的生效，必须读回计算值 |
| `web-research` | 调研 | `/rsearch` | 详情点击后异步渲染；调研成果必须沉淀进知识库 |
| `site-assistant` | 客服 | `/assistant` | 对话与页面操作交错：只改目标、读回状态再回话 |

新增剧本后要跑一遍：

```powershell
npm test               # 单元 + 门禁 + 刷新测试数
npm run test:e2e       # 真实 Chromium
node scripts/gen-capability-inventory.mjs   # 若 npm test 提示清单不一致
```

### T1 · 真实站点实验室（新增一层，手动，不进 CI）

**这是本方案最缺的一层。** 复用同一套 harness，只把夹具页换成真实 URL：
脚本化模型不变（协议是真的、生产代码是真的，只有"模型决定"被换成脚本），
因此它验证的是**定位器/时序/登录态在真实 DOM 上的成色**，而不是花真钱。

落地为 `tests/e2e-live/`（见该目录 README 与 `sites.mjs`）：

- 每条 `{ url, storageState, instruction, script, checks }`，按站点配置脚本化工具序列与页面判据；
- 用环境变量 `E2E_LIVE=1` 显式打开，默认不跑、不进 CI；
- 登录态用 Playwright `storageState` 持久化，跑前手动登录一次；
- 判据沿用仓库纪律：看**站点自己的数据**（搜索结果里的真实标题、草稿箱真的多了一条），
  而不是「工具返回 ok」。

第一批真实站点清单（按风险从低到高推进）：

| 站点 | 验证什么 | 备注 |
| --- | --- | --- |
| 百度/必应搜索 | 真实搜索 + 结果翻页 + 广告混排 | 无需登录 |
| 一个电商详情页 | shadow DOM、异步加载、规格 SKU | 无需登录 |
| 知乎/文档站长文 | 调研、划重点、摘录、存知识库 | 无需登录 |
| 小红书发布页 | 发图文草稿 | 测试号 + **草稿模式**（见纪律） |

### T2 · 真模型 + 真实站点（手动、按需、花钱）

`scripts/eval-real-model.mjs` 已有真模型模式，给它加一个 live 站点变体
（指向 T1 的站点清单，复用同一套 pageChecks）。这一层只回答两个问题：
「做成了但绕了远路」（文案不够省 → 改 skill）或「根本没找到页面能力」（工具/提示问题）。
失败先打印工具轨迹再动手 —— 见 [real-model-eval-log.md](real-model-eval-log.md) 的纪律。

### T3 · 自用埋点（把「用一阵子」变成数据）

run trace 已在采每一步（工具、耗时、token、错误、缓存命中），缺一个**聚合 + 导出**的口。
给 `get_run_trace` 之上加轻量聚合：每任务的轮次 / 工具调用数 / 缓存命中率 / 重试 /
工具摘除次数 / `expand_result` 往返，以及每个 skill 的加载频率与完成率。
日常用一周的数据，比人工设计更能告诉你"编排哪里在空转"。

## 三、改进闭环：失败归因 → 修法 → 沉淀

每个失败先归到**三类之一**，修法完全不同（仓库已验证过的结论）：

| 失败形态 | 例子 | 修法 | 沉淀成什么 |
| --- | --- | --- | --- |
| 能力缺口 | `type_text` 声明 5 个定位参数、实现只转发 2 个 | 补实现 | 行为剧本 + 静态门禁 |
| 技能文案 | 真模型美化时漏改宽容器 | 改 skill 编号步骤 + 判据 | 真模型 eval 再跑一次 |
| 编排逻辑 | 多绕 8 轮才做到 | 改编排/工具说明/并行白名单 | 埋点指标 + 回归剧本 |

**skill / 工具定义**的抓手，按性价比：

1. 新剧本自动喂给契约门禁（改 `playbooks.mjs` 即可，零额外测试代码）；
2. 加一道「schema 承诺 ↔ 实现能力」漂移门禁：把 schema 声明的定位/输出参数与
   `firstTarget` / `findElementsFor` / 各 handler 实际消费的字段对照；
3. 工具数（44）继续瘦身的决策，用 T3 的**引用密度数据**来决定（见
   [next-steps-handoff.md](next-steps-handoff.md) 的第 8/9 档取舍）。

**agent 编排**的抓手：

1. 先建基线指标（T3 埋点），再谈优化；
2. 优先查已知空转点：大结果截断阈值 6000/3000 与 `expand_result` 往返的平衡、
   并行白名单是否真的让高频只读工具并行、完成前校验成本、意图路由 promotion；
3. 每优化一项就回跑对应剧本 + 真模型 eval，并把改进前后记进 `real-model-eval-log.md`。

## 四、落地节奏（每阶段可交付、可验收）

- **P0**：补 4 个 T0 剧本 + 各自技能；`npm test` 与 `npm run test:e2e` 全绿（本批已做，待 E2E 复核）。
- **P1**：搭 `tests/e2e-live/` 骨架 + 第一批真实站点；跑通 2–3 个（百度搜索、电商详情、文档站），
  记录真实 DOM 上的定位问题清单。
- **P2**：真模型 eval 打这批真实站点（小红书用草稿模式）+ 完成 T3 埋点聚合导出。
- **P3**：按三类归因修 skill / 工具 / 编排，每修一项就加门禁或剧本，不让同样的问题复发两次。

## 五、纪律（照抄仓库既有教训）

- 小红书只做**草稿**（保存草稿，绝不自动发布），最好用测试号；
- 真模型 eval 永不进 CI（花钱且非确定）；真实站点不稳定，T1 只手动跑、失败不追绿；
- 无头环境下 MV3 service worker 不注册，真浏览器测试都要有显示（Linux 用 xvfb-run）；
- 改 `lib/page/**` 或 `lib/shared/**` 后必须 `node scripts/build-content.mjs`；
- 别用 PowerShell 改写源文件（会破坏 UTF-8，此前写坏过 `golden.spec.mjs`）；
- 剧本一次只做一类；「一次就过」先怀疑有没有真的跑到那条分支（本仓库已踩过四次）。
