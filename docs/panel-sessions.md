# 面板会话：全浏览器共享、历史与运行锁

面板对话不再按标签页隔离：会话正文与索引持久化在浏览器共享的 IndexedDB
`recallflow-history` 中，面板开合/运行锁等临时状态保存在 `chrome.storage.session`。
打开任意网页，面板默认进入同一个“当前会话”；浏览器重启后历史仍然保留。

## 用户可见行为

- 标题栏「会话」按钮列出历史会话，显示标题、更新时间、消息数、token 估算和是否正在运行。
- 「新建会话」保留旧会话；旧的「清空对话」不再删除历史。
- 切换会话会恢复该会话的消息、工具步骤、计划条与交接标识。
- 每个会话可重命名、删除或单独导出为 Markdown。
- 空闲标签页会跟随全局当前会话；运行中的标签页固定在原会话，等本轮结束后再同步，避免输出被切走。
- 面板打开/关闭同样全浏览器同步：任一页面打开或关闭面板，其他已注入页面立即跟随；新页面加载时继承当前状态。
- 运行中的思考、正文、工具步骤与计划会实时同步到打开同一会话的其他标签页；跟随页只读，结束后恢复输入。
- 同一会话同时只允许一个标签页运行 Agent。第二个标签页会提示“接管并运行”或“新建会话”。
- **整页跳转不新建空会话**：跳转后新页面可能还在等 Service Worker 启动，
  `panel:state` / `panel:get` 会重试；若历史会话存在但正文暂时读不出，面板显示
  “会话内容暂时读取失败”，而不是悄悄建一个空会话（那会把白屏伪装成新会话）。
- **同 tabId ≠ 同页面实例**：跳转会复用 tabId，`panel:run:subscribe` 现在总是返回
  snapshot，由面板判断“本页是否真的在跑这个 runId”；新页面会跟随原 run，
  并在连续约 10 秒没有新 delta 时回落到落盘会话（发起页的 agent 循环已随跳转终止）。
- **运行中空白自愈**：面板每 1.5 秒检查一次流式块是否还在（flow 是否连着、里面有没有内容、
  正在输出的那条消息是否还在文档里）；丢失时重建，并 `console.warn` 记录会话数、运行态、
  parts 数、修复次数。重连快照重建（先清空再铺回）若中途抛错，会显示
  “恢复输出时渲染失败：…”而不是留下空白。修复有 3 秒冷却 —— 自检本身不该变成新的闪烁源。

## 存储模型

所有写入都由 Service Worker 串行完成，内容脚本只发消息和渲染。

| 存储位置 / key | 内容 |
| --- | --- |
| IndexedDB `panel-kv` / `recallflow.psess.index.v1` | `{ version, seq, sessions }`，列表摘要、字符/字节/token 统计 |
| IndexedDB `panel-kv` / `recallflow.psess.v1.<id>` | 单个会话的**完整消息**、标题、交接标识、最后 runId |
| IndexedDB `panel-kv` / `recallflow.psess.active.v1` | 全浏览器当前会话 `{ id, seq, updatedAt }` |
| session storage / `recallflow.psess.ui.v1` | 面板开合状态 `{ open, seq, openTabs, updatedAt }` |
| session storage / `recallflow.psess.lock.v1.<id>` | 运行锁 `{ runId, tabId, at }`，TTL 120 秒 |

保存只重写当前会话与索引，不会把所有历史会话反复写一遍。会话正文使用完整副本，
不再套用导出侧的“最近 20 条消息 / 2KB 工具结果”裁剪。默认保留最多 1000 个会话；
单个会话超过 **1,000,000 estimated tokens** 时只显示预算警告，不自动删除。

## 并发规则

- 每次保存携带 `baseSeq`。不同标签页基于旧版本写入时会被拒绝，避免静默覆盖。
- 同一标签页的连续保存允许追平 `seq`；跨标签页仍走冲突保护。
- 运行前先获取会话锁；心跳每 20 秒续期。标签页关闭会由 `tabs.onRemoved` 主动释放锁，
  崩溃等情况则由 TTL 兜底。
- 接管会通知原标签页停止本轮，避免两个页面同时操作同一段对话。
- `openTabs` 区分“用户主动关闭面板”和“某个标签页被关闭”：前者广播关闭所有页面，
  后者只移除当前成员；最后一个显示面板的标签页关闭时才把全局状态改为关闭。

## 迁移

首次打开面板时：

1. 旧 `chrome.storage.session` 中的 `recallflow.psess.*` 会复制到 IndexedDB；
2. 更早的 `recallflow.conv.<tabId>` 会迁成历史会话；
3. 迁移完成后删除旧 key，索引已存在时不会重复迁移。

## 运行流同步

Agent 事件先进入 Service Worker 的 `RunStreamHub`，再由它定向广播给订阅了同一会话的标签页：

- `chunk` / `reasoning` 按约 40ms 合并，避免逐 token 跨进程发送；工具、计划、审批状态等结构化事件立即广播。
- 每个 run 维护单调递增的 `cursor` 和完整 live 状态。中途打开、刷新或漏收消息的标签页先取 snapshot，再从下一个 cursor 跟增量。
- SW 与跟随页共用 `applyRunEvent` 纯函数，思考、叙述、工具步骤的顺序不会出现两套实现漂移。
- 跟随页不写持久化层，只渲染临时 live 消息；发起页在结束时把正式消息写入 IndexedDB，随后跟随页自动刷新并恢复输入。
- 跟随页的“参考来源”只列正文实际写到的 `[n]`，并按首次出现顺序重编号；仅登记但未被引用的页面不会凭空出现在来源区。来源区与发起页一样只在 run 收尾后显示，流式过程中不提前出现。
- 完成前校验、意图识别、预算停止等过程提示会写入 assistant `parts`，任务收尾或重新打开面板后仍保留。
- Agent 打开的辅助标签页采用两阶段清理：先登记待关闭页，发起页确认最终回复已写入共享会话后才真正关闭；发起页异常时由后台 15 秒兜底清理。
- 截图只同步“已生成”的步骤，不广播 base64 图片数据，避免把几百 KB 的图像塞进高频事件流。

## 渲染稳定性（防白闪）

面板的两种症状——「一闪一闪」和「流式回答白屏」——往往同源：**同一条消息被反复重建**。

纪律：

1. **内容没变就不重建**。`renderConversation` 先算一个内容指纹（每条的 role、正文长度与
   首尾片段、parts 数量与长度、引用 id、计划、live/failed/interrupted 标记），并与
   `panelBody` 里真实的消息节点数核对；指纹相同且 DOM 完整时直接返回。指纹只在
   `removePanel` / 宿主被摘掉时作废（新面板是空 body）。
   显式需要重画的入口传 `force: true`（截图重绘、撤销、重新生成、收尾落盘）。
2. **流式块幂等**。`mountLiveStreamingBlock` 复用一个仍然连着面板的 `.msg.ai`，
   只重画它内部的 flow；只有它真的不在了才新建。这样自检、跟随页刷新、正文重建
   都不会留下第二份或造成"闪一下又回来"。
3. **不往脱离文档的节点里写正文**。chunk 到达时与每帧重绘前都检查
   `pendingContentEl.isConnected`；不在文档里就把流式块接回来，而不是继续往哑节点里画
   （症状是"日志一直在输出，屏幕上却是白的"）。
4. **计划条按指纹重画**。跟随页路径每帧都会调用 `renderPlan`，它现在只在计划内容或
   用户的展开/折叠选择变化时才碰 DOM，也不在那条路上无谓地触发 `fitPanelHeight()`。
5. **自检修复有冷却**（3 秒）。自检是为了兜底，不能变成新的闪烁源。
6. **正文里只有一条"当前回答"**。流式块（`data-rf-live`）、跟随页覆盖层（`.follow-live-ai`）
   是同一件事的两种画法，任何时刻最多存在一条：`mountLiveStreamingBlock` / `run()` 新建
   之前先 `pruneLiveBlocks(keep)` + `sweepFollowOverlay()`，收尾时也扫一遍孤儿块。
   否则旧的那条会带着半截内容留在正文里，置底还会停在一个不再更新的块上 —— 看起来就是白屏。
7. **`renderConversation` 只渲染落盘对话**（`panelSessionState.conversation`），**不渲染**
   `followedMessages`：跟随内容由跟随页自己的覆盖层负责。这条是"跳转后正文里同时出现
   半截回答与完整回答"的根因 —— 会话落地那次重绘把跟随快照当成正式消息画了一遍。
8. **续跑/接管时丢掉半截 assistant 尾**：`pruneResumableAssistantTail` 现在把
   "`live`/`interrupted` **或正文为空**"的 assistant 都视为半截（收尾入库的那条一定有
   content），并且在 `adoptPanelSession` 里也会对"运行中落地的会话"做一次同样的清理。
9. **新一轮开始前摘掉"空对话占位"**：占位也是一个 `.msg` 节点，留着会让 DOM 节点数恒比
   对话多一个 ⇒ 第 1 条的短路永远失效（划词/自检每来一次就整块重建 = 白闪）。
10. 2 秒内重建 5 次会在控制台留下告警，列出每次重建的 `reason`。
11. **诊断随记录一起走**：导出/交接记录末尾会附一段「面板诊断」（视口、面板/正文尺寸、
    最近 60 条"重建/挂载/摘块"事件）。白屏/白闪只在真实页面偶发，这段是事后唯一能还原
    先后顺序的证据 —— 用户点一下「导出」或「交接」就能把它带出来。
12. **跟随层撤掉不等于把正文清空**。实测最刺眼的一条（导出记录的「面板诊断」里看得很清楚）：
    两个 `follow-reset` 都发生在落盘对话只有 1 条（用户那条）时，之后 19 秒正文里只有用户消息。
    根因是撤跟随层时正文只能从落盘会话重建，而那一轮的回答还在发起页手里。
    现在的纪律：
    - `resetFollowedRun` 在撤层之前先把**已知的部分回答**补成一条本地兜底消息
      （`partialFromFollow`，不落盘、不参与持久化），所以正文永远不会只剩用户那条；
    - `scheduleFollowedRunRefresh` 在"还没落盘"时**不许收摊**：前 6 次 300ms、之后 1 秒一次，
      最多约 20 秒，等到正式回答落盘就整份替换；
    - 只有确实等不到才 `follow-giveup`，而那时兜底消息已经在了。
13. **每种撤层都带 `reason`**（`follow-committed` / `follow-not-running` / `follow-no-run` /
    `subscribe-*` / `follow-adopted` / `follow-giveup` / `follow-settled`），时间线里能直接看出是**谁**在撤。
14. **一个 run 只允许"跟随到底"一次**（`followedRun.settledRunId`）。实测缺陷：跟随页发现
    "已落盘"就撤层重建，而 SW 侧那个 run 的快照仍可能被再次订阅到 —— 于是
    「订阅 → 跟随 → 判已落盘 → 撤层强制重建 → 再订阅」形成自激活循环：
    **19 秒内 58 次整段重建**，11,592px 的对话每次都全量重排，表现正是「卡顿 / 白屏」。
    现在：收尾时记住 runId，之后该 run 的快照/增量（含迟到 delta）一律忽略；
    新 run（runId 变化）、本页自己发起新一轮时才清空这个标记。
15. **撤跟随层不再无条件重建**：先摘掉临时覆盖层，再用内容指纹决定要不要重建 ——
    覆盖层摘掉后正文与落盘会话完全一致时，重建毫无意义。
16. **跟随页的正文重绘与发起页共用同一套自适应节流**（`throttleStreamPaint`）。
    发起页早就有；跟随页原先逐帧重解析累积全文（长度上超线性），是"流式同步卡顿"的主因。

## 验证

- `tests/panel-sessions.test.mjs`：迁移、过期写入、同 tab 连写、锁冲突 / TTL / 关页释放、裁剪、并发创建。
- `tests/run-hub.test.mjs`：事件归约、40ms 合并、快照隔离与结束冲刷。
- `tests/resume-conversation.test.mjs`：续跑时只清理当前指令之后的半截回答，正式回答与前面几轮不受影响。
- `tests/e2e/blank-panel.spec.mjs`：**白屏/白闪/重建风暴回归门禁**。在流式窗口内每 30ms 采样
  面板正文（可视字数、消息节点数、每条 ai 块长度、滚动位置、面板高度，以及**整段重建次数**——
  用一个哨兵属性判断树有没有被换掉），覆盖 9 个场景：纯流式、流式中划词、流式中关面板再开、
  流式中整页跳转、思考流、多步工具、另一标签页跟随、**运行中才打开的跟随页**（对应 `open_tab`
  换页，实测就是在这个形态下白屏）、小视口。断言"看不见任何正文"≤400ms、跟随页整段重建
  次数 ≤8（实测缺陷是 19 秒 58 次），并打印正文骨架。
- `tests/e2e/sessions.spec.mjs`：新建并切回历史、跨 tab 加载与 active 同步、面板开合双向同步，以及中途加入后继续看到思考/正文增量。
- `tests/e2e/persistence.spec.mjs`：关闭整个浏览器上下文，再用同一用户数据目录重启，验证 IndexedDB 历史仍存在。
